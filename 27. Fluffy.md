> [!NOTE] **Shadow Credentials**
> **Shadow Credentials** — это атака на Active Directory, которая использует возможность добавления асимметричных ключей (Key Credentials) в атрибут объекта msDS-KeyCredentialLink. Этот атрибут используется механизмом Microsoft Windows Hello for Business и PKINIT в Kerberos.
> 
> Суть атаки:
> 
> 1. Атакующий получает право изменять объект AD (например, через GenericWrite, GenericAll или WriteProperty).
> 2. В объект жертвы (обычно пользователя с высокими привилегиями) добавляется собственный публичный ключ в атрибут:
> ```
> msDS-KeyCredentialLink
> ```
> 3. Теперь атакующий может использовать свой приватный ключ для аутентификации от имени этого пользователя через Kerberos PKINIT.
> 4. В результате получается Kerberos TGT (Ticket Granting Ticket) пользователя-жертвы.
> 5. Этот TGT можно использовать для доступа к ресурсам или дальнейшей эскалации привилегий.

Подобное объяснение техники ESC16
### Сначала вспомним, как происходит аутентификация по сертификату

Представим, что пользователь **Alice** получает сертификат от корпоративного CA.

В сертификате могут быть различные идентификаторы:

- Subject
- SAN UPN = `alice@corp.local`
- SAN DNS
- **SID Extension** (`szOID_NTDS_CA_SECURITY_EXT`)

Когда Alice предъявляет сертификат контроллеру домена (PKINIT), DC должен понять:

> **"Какому объекту Active Directory принадлежит этот сертификат?"**

До 2022 года ответ был довольно простым.

DC смотрел примерно так:

```
SAN UPN = administrator@corp.local

↓

Ищу пользователя с таким UPN

↓

Нашёл Administrator

↓

Выдаю TGT
```

То есть доверие строилось только на имени.
### В чем проблема такого подхода?

UPN — это обычный атрибут Active Directory.

Например

```
Administrator
    UPN = administrator@corp.local

Bob
    UPN = bob@corp.local
```

Если злоумышленник может изменить UPN пользователя Bob

```
Bob
UPN = administrator@corp.local
```

то сертификат Bob уже будет содержать

```
SAN UPN = administrator@corp.local
```

И если DC доверяет только UPN, он подумает

> "Это сертификат администратора."

Хотя сертификат принадлежит Bob.

Именно это и лежало в основе старых атак AD CS.

### Microsoft решила эту проблему

После патча KB5014754 Microsoft сказала:

> "Хватит доверять только UPN."

Теперь CA начинает автоматически добавлять в сертификат

```
SID Extension
```

Например

```
SAN UPN = administrator@corp.local

SID =
S-1-5-21-111-222-333-500
```

Этот SID нельзя просто взять и поменять через изменение UPN.

Он берётся непосредственно из объекта AD при выпуске сертификата.
### Что теперь делает DC

Теперь логика выглядит иначе.

Раньше

```
Смотрю UPN

↓

Нашёл пользователя

↓

OK
```

Теперь

```
Смотрю SID

↓

Нашёл объект с этим SID

↓

Это именно тот пользователь

↓

Выдать TGT
```

То есть SID становится настоящей "привязкой личности".
### Тогда что такое ESC16?

Вот здесь начинается сама техника.

Представим, что администратор по какой-то причине говорит CA

> "Не добавляй SID Extension вообще."

То есть CA снова начинает выпускать сертификаты старого образца.

Например

```
SAN UPN = administrator@corp.local

SID Extension

НЕТ
```

Именно это называется ESC16.

То есть проблема не в шаблоне.

Проблема во всём удостоверяющем центре.

Все сертификаты этого CA будут выпускаться без SID.
# Почему это опасно?

Потому что DC оказывается вынужден использовать старый механизм.

Он получает сертификат

```
UPN = administrator@corp.local

SID отсутствует
```

И думает

```
Ну SID нет...

Тогда использую старую схему

↓

ищу пользователя по UPN
```

И снова появляется возможность обмануть DC.

# Тогда где здесь сама атака?

Теперь разберём её по шагам.
## Шаг 1

Есть пользователь

```
Hacker
```

У него есть GenericWrite на другого пользователя

```
ESC16User
```

## Шаг 2

Он меняет UPN этого пользователя.

Было

```
ESC16User

UPN

esc16user@good.expert
```

Стало

```
ESC16User

UPN

Administrator@good.expert
```

Заметь

Он **не стал администратором**.

Он просто поменял один LDAP-атрибут.

## Шаг 3

Теперь он аутентифицируется как ESC16User и просит сертификат.

CA смотрит

```
UPN пользователя

↓

Administrator@good.expert
```

и выпускает сертификат

```
SAN

Administrator@good.expert
```

Но поскольку CA уязвим (ESC16),

SID не добавляется.

Получается сертификат

```
UPN = Administrator

SID = отсутствует
```

## Шаг 4

Теперь злоумышленник предъявляет этот сертификат DC.

DC получает

```
UPN = Administrator

SID отсутствует
```

Если DC работает в режиме совместимости (StrongCertificateBindingEnforcement = 0 или 1), он говорит

```
SID нет

↓

использую UPN

↓

Administrator найден

↓

выдать TGT Administrator
```

Именно так злоумышленник получает билет администратора без знания его пароля.

# Почему ESC16 опаснее ESC9?

Это самый важный момент статьи.
### ESC9

Уязвим только один шаблон.

```
Template A

↓

без SID

Template B

↓

с SID

Template C

↓

с SID
```

Проблема локальная.

### ESC16

SID отключается прямо на CA.

Получается

```
CA

↓

Template A

без SID

↓

Template B

без SID

↓

Template C

без SID

↓

Template D

без SID
```

То есть вообще любой шаблон этого CA становится потенциально пригодным для атаки (если выполняются остальные условия: Client Authentication, Enroll и возможность подменить идентичность).
