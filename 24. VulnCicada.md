Уязвимых сертификатов нет, но центр сертификации уязвим для ESC8, поскольку включена регистрация через HTTP-веб. Для эксплуатации этой уязвимости нам нужно обмануть контроллер домена, чтобы он аутентифицировался у нас, а затем перенаправить аутентификацию на эту конечную точку и таким образом получить сертификат от имени контроллера домена. Проблема этого подхода заключается в том, что самостоятельная пересылка NTLM блокируется, а аутентификация NTLM в целом отключена в этом сценарии, поэтому наш единственный вариант — использовать Kerberos-relay.

В этой [статье](https://www.synacktiv.com/publications/relaying-kerberos-over-smb-using-krbrelayx.html) описано, как мы можем осуществить Kerberos-Relay, используя SMB с особым DNS-именем. 


> [!NOTE] **Суть Kerberos-Relay**
> В классическом исполнении, ESC8 работает через NTLM, и атака выполняется в 5 этапов:
> 1. Злоумышленник находит уязвимый AD CS веб-сервис (`http://ca-server/certsrv/`)
> 2. Далее злоумышленник, обычно через уязвимость, принуждает контроллер домена к NTLM-аутентификации на свой подставной сервер(Например `PetitPotam`).
> 3. После этого, злоумышленник перенаправляет полученный запрос NTLM-аутентификации на веб-сервер AD CS
> 4. Злоумышленник получает сертификат от центра сертификации. Этот сертификат подтверждает личность контроллера и может использоваться для аутентификации в сети.
> 5. С полученным сертификатом злоумышленник может запросить TGT у службы Kerberos и аутентифицироваться в домене от имени контроллера домена. Для этого применяются инструменты вроде Rubeus или Certipy. Получив TGT, он получает те же полномочия, что и реальный контроллер, включая доступ к системным API, возможность управления объектами AD и выполнение DCSync (репликация базы `NTDS.dit`, содержащей все хеши паролей в домене).
> 
> В данной лабораторной работе, авторизация по NTLM отключена, тут используется Kerberos, из-за этого эксплуатация уязвимости меняется. Вот статьи по этой теме - [статья1](https://www.synacktiv.com/publications/relaying-kerberos-over-smb-using-krbrelayx.html), [статья 2](https://www.thehacker.recipes/ad/movement/kerberos/relay#:~:text=ADCS_FQDN%20%2Dv-,Abuse%20from%20a%20coerced%20authentication,class%20of%20service%20cifs%2C%20the%20returned%20SPN%20will%20look%20like%20%3A,-cifs/target1UWhRCAAAAAAAAAAUAAAAAAAAAAAAAAAAAAAAAtargetsBAAAA). 
>
 > Теоретически, ретрансляция Kerberos довольно проста. Цель состоит в том, чтобы переслать сообщение AP_REQ, инициированное клиентом для одной службы, другой. Однако существует одно важное условие: **целевая служба и клиент не должны требовать шифрования или подписи, поскольку у нас нет секрета (ключ сессии)**, необходимого для выполнения этих операций, аналогично атаке с использованием NTLM-ретранслятора.
> 
> **Также существует дополнительная сложность: сообщение AP_REQ не может быть переслано другой службе, работающей под другим идентификатором, отличным от того, который изначально запросил клиент**. Поэтому для успешной атаки нам необходимо заставить клиента сгенерировать сообщение AP_REQ для целевой службы и отправить его нам
> 
> ##### Общая идея атаки
> 
> Цель атаки — заставить доверенный компьютер (например, контроллер домена) выполнить Kerberos-аутентификацию к SMB-серверу злоумышленника, а затем без изменений переслать (relay) полученную аутентификацию другому сервису, например ADCS. В результате клиент считает, что подключается к одному серверу, а злоумышленник использует полученное Kerberos-сообщение для аутентификации перед целевым сервисом.
> 
> В классическом сценарии взаимодействие происходит напрямую:
> ```
> DC ──Kerberos──► ADCS
> ```
> 
> При Kerberos Relay цепочка выглядит иначе:
> ```
> DC ──Kerberos──► SMB злоумышленника
>                      │
>                      │ Relay
>                      ▼
>                   ADCS (HTTP)
> ```
> ##### Kerberos Relay долгое время считался невозможным
> В случае NTLM relay работает достаточно просто: злоумышленник получает challenge-response клиента и пересылает его другому серверу. Поскольку NTLM не привязывает аутентификацию к конкретному сервису, сервер может принять пересланные данные.
> 
> С Kerberos ситуация принципиально отличается. Перед подключением клиент запрашивает у KDC сервисный билет (TGS) строго для определенного SPN (Service Principal Name). Например, при подключении к файловому серверу билет будет выписан для SPN:
> 
> ```
> cifs/fileserver
> ```
> 
> Этот SPN содержится внутри Service Ticket, который затем передается серверу в сообщении AP_REQ. Если злоумышленник попытается переслать такой билет сервису с другим SPN, например:
> 
> ```
> http/pki
> ```
> 
> сервер не сможет расшифровать билет, поскольку он был выписан не для него. Именно поэтому долгое время считалось, что классический Kerberos Relay невозможен.
> 
> ##### Как удалось обойти это ограничение
> 
> Основная идея исследования заключается в том, чтобы разделить два понятия:
> - имя, используемое для DNS-подключения;
> - имя (SPN), для которого KDC выпускает Kerberos-билет.
> 
> **Если заставить Windows подключиться к серверу злоумышленника, но при этом запросить билет для легитимного сервиса, то полученный AP_REQ можно будет успешно переслать настоящему серверу.**
> 
> Ключевую роль в этом играют функции `CredMarshalTargetInfo()` и `CredUnmarshalTargetInfo().`
> 
> ##### Формирование SPN при подключении к SMB
> 
> При подключении к ресурсу вида:
> 
> ```
> \\fileserver
> ```
> 
> Windows автоматически формирует SPN:
> 
> ```
> cifs/fileserver
> ```
> 
> Для этого используется функция `SecMakeSPNEx2()`, которая строит имя сервиса, для которого затем будет запрошен TGS.
> 
> Однако Microsoft предусмотрела поддержку специальных структур Credential Target Information, применяемых Credential Manager. Перед формированием SPN информация о целевом сервере может быть сериализована функцией CredMarshalTargetInfo().
> Например, структура:
> 
>```
> TargetName = fileserver
> Package = Kerberos
>```
> 
> преобразуется в специальную строку, напоминающую Base64:
> 
> ```
> 1UWhRCAAAAAAAAAAUAAAAAAAA...
> ```
> 
> После этого Windows может сформировать имя:
> ```
> fileserver1UWhRCAAAAAAAAA...
> ```
> 
> Внешне это выглядит так, словно к имени сервера просто добавлен длинный суффикс.
> Где появляется возможность для атаки
> Предположим, злоумышленник создает DNS-запись:
>
>```
> fileserver1UWhRCAAAAA...
>         │
>         ▼
>    IP злоумышленника
>```
>
> Когда Windows подключается к этому имени, происходит несколько важных событий.
> Сначала система вызывает `CredUnmarshalTargetInfo()`, которая распознает специальный сериализованный суффикс и извлекает исходное имя сервера:
> 
> ```
> TargetName = fileserver
> ```
> 
> После этого SPN формируется уже без добавленного суффикса, поэтому клиент запрашивает у KDC билет для:
> 
> ```
> cifs/fileserver
> ```
> 
> Однако сетевое соединение (TCP) устанавливается не с настоящим файловым сервером, а с DNS-именем:
> 
> ```
> fileserver1UWhRCAAAAA...
> ```
> 
> которое разрешается в IP-адрес злоумышленника.
> 
> Именно здесь возникает ключевой эффект всей атаки: физическое соединение устанавливается с атакующим, но Kerberos-билет оказывается действительным для настоящего сервиса.
> 
> ##### Почему билет можно переслать
> 
> Полученный Service Ticket был выписан KDC именно для SPN:
> 
> ```
> cifs/fileserver
> ```
> 
> Следовательно, настоящий файловый сервер также сможет успешно его расшифровать, поскольку использует тот же SPN.
> Сам злоумышленник билет расшифровать не может — у него нет соответствующего ключа. Однако для Relay это и не требуется. Ему достаточно принять Kerberos-сообщение целиком и переслать его дальше без каких-либо изменений.
> 
> ##### Использование DNS и coercion
> 
> В демонстрации авторы создают DNS-запись примерно следующего вида:
> ```
> pki41UWhRCAAAAA...
>         │
>         ▼
> IP злоумышленника
> ```
> 
> После этого с помощью техники принудительной аутентификации (например, PetitPotam) контроллер домена заставляют подключиться к ресурсу:
> 
> ```
> \\pki41UWhRCAAAAA...
> ```
> 
> Контроллер домена выполняет стандартную процедуру Kerberos-аутентификации:
> 1. разрешает имя через DNS;
> 2. получает IP-адрес злоумышленника;
> 3. восстанавливает исходное имя сервиса через CredUnmarshalTargetInfo();
> 4. запрашивает у KDC сервисный билет (TGS) для:
> ```
> cifs/pki4
> ```
> 5. получает билет;
> 6. отправляет его злоумышленнику внутри сообщения AP_REQ.
> 
> ##### Что содержит AP_REQ
> Сообщение AP_REQ представляет собой полноценную Kerberos-аутентификацию клиента перед сервисом. В его состав входят:
> 1. **Service Ticket (TGS)** — сервисный билет, выданный KDC для конкретного SPN;
> 2. **Authenticator** — структура, подтверждающая, что клиент действительно владеет соответствующим сеансовым ключом.
> 
> Именно AP_REQ передается серверу при установлении Kerberos-сессии.
> 
> ##### Как работает krbrelayx
> 
> SMB-сервер злоумышленника принимает AP_REQ, но не пытается расшифровать содержащийся в нем билет. Вместо этого он просто сохраняет все полученные байты Kerberos-сообщения и устанавливает новое соединение с целевым сервисом, например ADCS.
> 
> Далее AP_REQ практически без изменений пересылается в HTTP-запросе:
> 
> ```
> Authorization: Kerberos <base64(AP_REQ)>
> ```
> 
> Фактически krbrelayx выполняет роль посредника, который не анализирует содержимое Kerberos-билета, а лишь передает его другому сервису.
> 
> ##### Почему ADCS принимает эту аутентификацию
> 
> ADCS доверяет билету, поскольку он был выдан контроллером домена (KDC), а клиент успешно прошел Kerberos-аутентификацию. В рассматриваемой атаке используется особенность конфигурации, при которой Kerberos-аутентификация, полученная через SMB, может быть использована для доступа к HTTP-службе ADCS, работающей на том же сервере.
> 
> Именно поэтому ADCS долгое время являлся одной из наиболее популярных целей для Kerberos Relay.
> 
> ##### Получение сертификата
> После успешного Relay krbrelayx автоматически обращается к веб-интерфейсу ADCS (например, /certsrv/certfnsh.asp) и запрашивает сертификат, используя подходящий шаблон, например:
> 
> ```
> DomainController
> ```
> 
> от имени контроллера домена:
> ```
> DC03$
> ```
> Если шаблон допускает такую выдачу, ADCS возвращает сертификат, например:
> ```
> DC03$.pfx
> ```
> 
> ##### Почему сертификат приводит к компрометации домена
> 
> Полученный сертификат можно использовать для аутентификации по PKINIT — расширению Kerberos, позволяющему получать TGT с использованием сертификата вместо пароля.
> Утилита gettgtpkinit.py выполняет запрос AS_REQ, подписанный полученным сертификатом, после чего KDC выдает полноценный TGT для учетной записи контроллера домена.
> Обладая TGT контроллера домена, злоумышленник может выполнять любые действия от его имени, включая проведение DCSync, что фактически означает полный компромисс домена.
> Полная цепочка атаки
> Вся атака выглядит следующим образом:
>```
> 1. Создается DNS-запись:
>    pki41UWhRCAAAAA... → IP злоумышленника
> 2. PetitPotam (или другая coercion-техника) заставляет DC
>    подключиться к этому имени.
> 3. Windows восстанавливает исходное имя через
>    CredUnmarshalTargetInfo().
> 4. KDC выдает TGS для SPN:
>    cifs/pki4
> 5. TCP-соединение устанавливается с IP злоумышленника.
> 6. DC отправляет AP_REQ злоумышленнику.
> 7. krbrelayx пересылает AP_REQ сервису ADCS.
> 8. ADCS выдает сертификат контроллера домена.
> 9. Сертификат используется для PKINIT.
> 10. KDC выдает TGT контроллера домена.
> 11. Полученный TGT используется для DCSync и дальнейшего
>     полного компрометации домена.
>```
>
> ##### Основная идея техники
> 
> Вся атака основана на особенностях работы CredMarshalTargetInfo() и CredUnmarshalTargetInfo(). Благодаря этим функциям Windows разделяет имя, используемое для DNS-подключения, и имя (SPN), для которого запрашивается Kerberos-билет. В результате клиент физически устанавливает соединение с сервером злоумышленника, но отправляет ему AP_REQ с билетом, действительным для легитимного сервиса. Именно это разделение DNS-имени и SPN делает Kerberos Relay через SMB возможным и лежит в основе всей рассматриваемой техники.
